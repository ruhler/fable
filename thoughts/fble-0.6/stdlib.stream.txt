The pattern I'm using is:
* What to do if the stream is empty. Just return a result based on current
  state.
* If the stream isn't empty, update the state based on the next value, do a
  recursive call, get back a result, and optionally process that result.

I would like to take advantage of the fact that the recursive call is my own
traversal. I don't need to change up the traversal. So if I were to write
something like the Update function in the cleanest way I could, it would be
something like:

  onEmpty = (Map@<K@, V@> map) {
    V@ value = with({
      map.?(empty: Nothing<V@>);

      # If you get a wrong tag access error here on map.entry, then your
      # data type violates the prefix property.
      Just(map.entry.value);
    });

    Map@(entry: Entry@(key, value));
  };

  onItem = (Map@<K@, V@> map, Bit@ x, (Map@<K@, V@>) { R@; } f) {
    children = {
      map.?(empty: @(0: Empty<K@, V@>, 1: Empty<K@, V@>));

      # If map.children access fails with wrong tag, it means your data
      # type didn't satisfy the prefix code requirement.
      map.children;
    };

    Map@<K@, V@> child = f(x.?(0: children.0, 1: children.1), key, with);
    x.?(
      0: Map@(children: children.@(0: child)),
      1: Map@(children: children.@(1: child)));
  };

  data(key)(onEmpty, onItem, map);

Does this look familiar to you? It looks familiar to me. The type is:

  <@ S@, @ R@>(
    (S@) { R@; } onEmpty,

My claim is this should be easier to consume than my current stream. You saw
above, the code is simpler. I don't have to extract out the item or the state,

The downside, presumably, is we have to take care of all those things when we

That's not so bad. Just annoying syntactically. Remember, we need to provide
two different functions any time we want to traverse a stream. Based on the
above, I feel like I want to put onEmpty last for constructing streams,
because that will lead to natural function bind. The onItem function is not
changing at all during construction: we just pass the same thing down
everywhere. But onEmpty definitely does change during construction.

We need the state argument to be mentioned explicitly. We need it to call
onItem. More importantly, we need it to make sure we don't start traversing
the rest of the data structure until we have the next state generated.

For example, if I reordered arguments, I would could end up with:

  ForEach = <@ K@, @ V@>(Map@<K@, V@> map) {
