How to document standard library?

Fbld doc comments aren't up to snuff, and I'm not going to bring them up to
snuff this late in the release.

But I might consider going through and rewriting all the existing doc
comments.

Here are accumulated concerns so far:

* It's hard to find where fble functions live
 - Anything I can do about that?
* A lot of the /Std/* documentation isn't very helpful.
  Consider rewriting it to be an explanation for how to use the functions
  instead of a description of what they are.
* Figure out how to properly document List@ type
 - Mix of poly, struct, and union all in one.
* How to document a poly? @func? @value?
* How to document methods of interface structs?
* How to document an interface function type, like Eq@?
* /Std/List/Eq% docs could be more precise and include examples.
* How to document internal functions, e.g. /Std/List/Sort%.Insert?
  Make sure this doesn't get shown in reference documentation.
  e.g. /Std/Int/Lit% internal helper functions.
* Should I add @example as a doc comment field? Seems useful?

If I were to do the sadly large undertaking of rewriting all the docs, how
would I approach it?
* Write the documentation as an explanation for how to use the functions.
* For list data type, and other things where I have a complex field:
 - Nest the doc comment things. For example:
  #  @field[@][items] A non-empty list.
  #   @field[T@][head] The first item in a non-empty list.
  #   @field[List@<T@>][tail]
  #    Everything after the first item in a non-empty list.
* For poly we can use @func or @value. Whichever is most useful.
* For methods of struct, nest @arg, etc. under @field.
* For internal functions, let's properly document, but add an @private tag
  somewhere.
* Is @example useful? I'm not sure. I can use @code if I want.

Basically, high level, don't worry about formalizing things with fbld. Worry
about having the right content in the source code for human readers. We can
worry about content for machine readers later.

This will be useful. I think it's worth trying. See how far I get. The more
consistency, clarity, etc. I can get with the documentation, the better.

---

* It's hard to find where fble functions live

This is exacerbated by heavy use of submodules in fble. Submodules are used
for:
* Breaking false recursive cycles between modules.
  e.g. Char -> Int -> Show -> Char
  vs.  /Std/Char% -> /Std/Int%, /Std/Int/Show% -> /Std/Char%
* Name conflict resolution. 
  e.g. /Std/Int%.Show versus /Std/Int/IntP%.Show.
* Avoiding pulling in false dependencies.
  Though I'm not sure how much this actually works in practice.

I think submodules are here to stay. The way to help with finding where fble
functions live in that case is:
* A search engine for functions, if/when fble goes mainstream.
* Man pages generated for functions that say what module they live in.
* An stdlib html doc that includes a summary of all the modules and the
  functions implemented inside.

I'm not going to worry about a search engine or man pages today. I think it's
worth trying to produce an stdlib doc from the doc comments, but I don't want
to get slogged down dealing with fbld issues this release. So let's try it,
see how far we can easily get, and as soon as it starts getting too
complicated, punt to a future release.

Where I think we'll run into trouble with fbld here:
* Make sure things like @field, @arg can take @field and @arg in their
  descriptions. This should be okay I think.
* Upper.Radix and Lower.Radix can't distinguish between Upper and Lower. The
  doc comments just have 'Radix' as the name.
  - So to start, just list everything, don't try to interpret the names?
