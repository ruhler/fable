Module Compilation
==================
A few things have come up to suggest revisiting how modular compilation works:
1. We added support for foreign function interfaces. That has replaced all
   builtin modules in practice.
2. I'm considering removing undef expression, because it seems to have much
   lower value now that we have foreign function interface.
3. I'm wondering if we should remove .fble.@ files, because maybe we don't
   need them anymore?
4. TODO item: Figure out why we see the same errors reported many times when
   we build and fix it.

Let's take a step back. Not worry about implementation. But think about an
ideal world where things just work right. What would that world look like?

* I could easy and clearly document the interface to a module without the
  implementation.
 - Like we can do with .fble.@ files and undef expressions today.
* The type for a prebuilt module is read from the prebuilt module code, so we
  don't have to keep it in sync with separate header or documentation files
  for correctness.
* The compiler will tell us if our header/documentation files are out of sync
  with our prebuilt module code.
* We have a way to efficiently read the type of compiled code without having
  to type check it again. To avoid duplicate error messages.

That last point sounds hard. Especially when interpreted code is involved. It
suggests I read a .fble file and all its dependencies, compute its type, then
store the type somewhere (generated .fble.@ file?). But if you change the
.fble file, I have to know the .fble.@ file is out of date and recompile it.

Thus the build system has to get involved, and we have to trust it or
duplicate the logic for it in the compiler itself.

Maybe we say that every .fble file has to have a corresponding .fble.@ file.
When you reference another .fble file, you read its type from the .fble.@
file. If you don't have a .fble.@ file, that's an error. But the compiler can
type check and generate a .fble.@ file for you if you want.

When you compile Foo.fble, you must either supply an existing Foo.fble.@ file
to type check against, or tell the compiler to produce the Foo.fble.@ file,
... or don't use the Foo.fble.@ file at all, for example for a top level main
module that isn't referenced anywhere else?

If you are using the interpreter, you are loading all the Foo.fble files
anyway. The only concern is if you depend on another precompiled module, it's
Foo.fble.@ file may not match the actual implementation. I suppose we have to
add a check somewhere. Maybe checksum the type when we load the precompiled
code to validate it.

Or, since Foo.fble.@ files are only needed with precompiled code apparently,
store them with the precompiled code itself. Though that makes it harder to
use as a standard form of documentation.

It seems the crux of my problem is:
1. I want documentation and type to be specified together.
2. I want compiled code and type to specified together.
3. I want documentation and compiled code to be separate.

That suggests we duplicate the type information.

Anyway, the key thing for modular compilation is that when I compiling some
module Foo.fble that depends on /Bar%, I don't read Bar.fble. I read the
already compiled type of Bar.fble, or the header file Bar.fble.@ which is
going to be checked against when compiling Bar.fble separately.

Straw proposal:
* Put module type and documentation spec in a .fble.@ file.
* When referencing another file, only ever use its .fble.@ file for type.
* Add a way to generate .fble.@ automatically from a .fble file.
* Always check the type of a .fble file against its .fble.@ file when
  compiling.
* Store a checksum of the type of a module with the compiled code for the
  module.
* Store a checksum of the types of anything a module depends on in the
  compiled code for the module.
* When loading/linking a module, verify the checksums of everything it depends
  on match what it was compiled against.

Tedious, but safe. Gives us a way to do documentation. A way to avoid
recompiling module dependencies. Freedom from concern that the precompiled
code got out of sync with its header file.

On the other hand, there's a fair amount of technical work needed to make this
happen:
* Auto generation of .fble.@ files.
* Checksumming of types.

Unless you want to use a copy o the .fble.@ file as a checksum and run the
type checker at load/link time to validate the type of the expected .fble.@
file matches the type of the actual .fble.@ file.

Anyway, seems like we want .fble.@ files to exist regardless.

Also: we don't want to rely on the precompiled code for type checking, because
I want to be able to compile a module without having access to the precompiled
code it depends on to run. That's only doable through separate type
specification, aka separate .fble.@ file.

The vision at the moment is:
* Every .fble file has a corresponding .fble.@
* The compiler can auto generate .fble.@ for you if you want.

What does this solve or not?
* If .fble.@ files are auto-generated, they don't have errors. Then you should
  only see an error for a module when compiling that module itself. So you
  know longer get duplicate errors when you build.
* If .fble.@ files are manually created, they could have errors. You'll still
  see all those errors repeated. That's probably okay.
* Option to pass expected type of main is orthogonal, and could be addressed
  separately.
* Be able to typecheck body of a let for more error messages at once should be
  punted to the next release.

Things to keep in this release:

Things to punt:
* Be able to typecheck body of a let where variables aren't all well typed.
* Require a .fble.@ file for every module.
 - But add support for auto-generating them if requested.

Look. I need to sit down and rethink how module loading should look in a new
world. It's going to take effort. I don't want to implement any of that this
release. But maybe we want to sit down and create a vision for it this
release?

Especially considering I don't use hand written builtin modules anymore.

Let's brainstorm then, from scratch. A future, perfect vision.

Module implementations are provided via:
* Hand written Foo.fble file.
* Already compiled code for a Foo.fble file.
 - e.g. FblePreloadedModule that lives in some library somewhere.

Types are provided via:
* Hand written Foo.fble.@ file.
* Foo.fble.@ file autogenerated from Foo.fble during typecheck.

For each module we have three sources:
* Foo.fble
* Foo.fble.@
* Foo.fble.so (or whatever library it lives in).

Any and all of these can be out of sync.

If you use Foo.fble for running code, you need to typecheck it again, which
means you need to have the Bar.fble.@ files available for what it depends on.

Option:
* Require Foo.fble.@ files to be shipped alongside Foo.fble.so files.
* Allow Foo.fble.@ files to be shipped inside Foo.fble.so files.

Foo.fble and Foo.fble.@ files are untrusted. Foo.fble.so are assume to have
already been type checked, but they can only be used with the versions of
other modules they were type check with.

Let's assume we have some magic checksum we can use to uniquely identify a
particular version of a Foo.fble.@ file. But assume it doesn't give us the
full type of the Foo.fble.@ file.

It's maybe also worth mentioning, for ffi code, you need some other code
sitting around somewhere. Maybe linked with your Foo.fble.so or otherwise a
clear dependency for anyone who is using Foo.fble.so.

Thus, the proposed structure is:

* Foo.fble (untrusted)
* Foo.fble.@ (untrusted)
* Foo.fble.so (or whatever library it lives in).
  Embedded Foo.fble.@.checksum for it and everything it depends on.
  Optional embedded Foo.fble.@ (trusted) for it.

The benefit of having a trusted embedded Foo.fble.@ file is what?
* We don't have to carry around separate external Foo.fble.@ files, which is
  convenient.

For a given module, I can either type check it, compile it, or run it.

To compile a module, I need to know the types of what it depends on:
* We need to read and typecheck Foo.fble.@ that we depend on.
* Or read and typecheck embedded Foo.fble.@ that we depend on.
* Verify the type against its own Foo.fble.@ file (in untrusted case).

If we have an embedded Foo.fble.@ file, we don't need it to be fble syntax. It
can be a direct encoding of the underlying FbleType type. Though honestly,
fble syntax is probably most convenient, given we want names of things and
sharing.

In this world, I want each module to be loaded separately via its public
facing entity, with dependency checksums validated at load time?

What if you have a module and its dependencies all in the same .so or
otherwise library? Then it shouldn't have to recheck the types and checksums.
That sounds fair to me. And potentially important to cut down on linking time:
basically you can ship a prelinked module.

But that brings back this question: what if you have prelinked a module that
someone else also wants to depend on? Is there any problem with that?

You could always manually inline all module dependencies into a module.
Prelinking is kind of like that: I don't have external dependencies, it's all
just me. But internally we don't treat it that way. We treat it as separate
modules with names. And if you have names, you have a chance for name
conflicts.

And it's not hard to imagine a world where you want to depend on two modules,
A and B, both of which depend on different versions of another module C, and
we should allow that. Or both of which depend on the same version of another
module C, and we should allow that and be able to share the implementation of
C in that case.

Perhaps, in general, we should think about there being a single 'public'
implementation of a module with a given name. To reference a module by module
path gives you the public module. But you could also reference a module
directly (via pointer instead of module path), and that lets you access
modules that you can't access by name. So we could have three variations of
module C: the one reference directly from A, the one referenced directly from
B, and the public one referenced via name /C%.

Which suggests we have a single registry/table mapping public module name to
direct module implementation. But you can also have additional modules
available that you can't refer to by name. They have to live in your .so file
somewhere. You can assume if you reference a direct module in code, you have
already type checked against it.

Which suggests, when I depend on a module, either I do it directly, or by
name. If I depend on a module by name, then I need to have the type checksum
of the module I depend on to make sure its type is what I require. If I depend
on it directly, then I don't.

From Foo.fble or Foo.fble.@ code, all references are by name, and I don't need
to have the type checksum, because I'm running typecheck again regardless.

Thus, what we can have is:
* A Foo.fble file.
* A Foo.fble.@ file.
* A library that contains:
 - A registry of public path name to module implementations
 - A collection of module implementations.

A module implementation can depend on other modules in one of two ways:
* Via name, with type checksum of expected/required type of the module.
* Directly. No type checksum required.

Every module implementation ought to have a type checksum of its type.

Simple straw proposal:
* Foo.fble files
* Foo.fble.@ files.
* A library contains:
 - A collection of module implementations.
 - Each module implementation stores its type checksum.
 - Module implementations can depend directly on other module implementations
   in the library. They are assumed to be well typed.
 - Module implementations can depend on public module paths; they must include
   the expected type checksum in the dependency link for the public module
   path.
* The external Foo.fble.@ is used for all public module references. You
  typecheck the Foo.fble.@ file and test its checksum against the module that
  depends on it. If they match, great. If they don't match, it's a link error.
* The available Foo.fble.@ files defines the registry of public named modules.
* You have to be in the same compiled (statically linked) library file to be
  able to reference another module directly. Otherwise you have to use the
  public name for the module and go through typechecking.
* That means it's not possible for two different libraries to share the same
  module implementation and both have direct access to it. At least one and
  maybe both libraries will have to access the module through its public path.

And the only future thing to consider is if I want to more easily be able to
bundle the Foo.fble.@ files (or compiled version thereof) into the library
alongside the module implementation.

Now then. What does this solve? What concerns do I still have?
* Clear spec for modules direct referring to other modules.
* Clear resolution of conflicts:
 - 1 public version of a module only.
 - You reference a module either directly, or via public name.
* Compiled modules can depend on non-compiled just fine.
 - Validation of types is done at link time via type checksums.
* There's a reasonable future where we could dynamically load modules or
  packages of modules.
* We load minimum needed dependencies for type checking, because we always use
  the Foo.fble.@ files for that.
* We avoid showing the same error for a Foo.fble file twice in a sequence of
  compilations. You'll only see it when compiling that module.
* We will show duplicate errors for Foo.fble.@ files. Tough luck. Deal with
  it. If you use auto-generated Foo.fble.@ files, that's not an issues.
* fble-cli, fble-app, etc. can embed the required type checksums and validate
  those when running.

There are still some details around how to find the Foo.fble.@ file and the
implementation associated with a given public module path. We can have a file
search path to find Foo.fble.@ and Foo.fble. How do we search for precompiled
implementations? We can search for a Foo.fble.so file. But in practice I
probably want to be able to search inside a package wide .so file that isn't
named the same as the module. So maybe we need a mapping some where from
package name to list of public modules provided by that package. Some way to
know if we need to dynamically load a package to get at the implementation of
a module that it provides.

Otherwise, this sounds like a reasonable vision to me.
